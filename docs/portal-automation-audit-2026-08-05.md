# Аудит автоматизации портала V2SD

Дата проверки: 05.08.2026  
Портал: `v2sportdress.bitrix24.ru`  
Источники: VibeCode API, локальный код интеграций, логи последних сделок/лидов, скриншоты настроек БП.

## Как проводилась проверка

Использованы доступные через VibeCode методы чтения структуры CRM: поля сделок, лидов и контактов, справочники стадий, источники, воронки сделок, последние 500 сделок и последние 300 лидов.

Документация VibeCode подтверждает два важных момента:

- `GET /v1/me` нужен агентам для получения машинного описания платформы и доступных возможностей.
- Для фоновых серверных задач подходит ключ `vibe_api_*`, а для встроенных приложений/пользовательского OAuth-контекста нужен `vibe_app_*`.
- В индексе документации есть разделы по Entity API, автоматизации, истории стадий, таймлайну и пользовательским полям.

Обновление после OAuth-авторизации: через `vibe_app_*` получена пользовательская сессия и выгружены шаблоны БП, активные экземпляры, список пользовательских роботов/активностей и триггеры. API отдал 22 шаблона БП, из них 12 относятся к CRM/смарт-процессам. Список кастомных роботов приложения пустой, а тело шагов внутри шаблона (`templateData`) list/search-методы не возвращают даже при явном `select`, поэтому действия внутри каждого шаблона нужно финально сверять через дизайнер БП в UI Bitrix24.

Локальная выгрузка лежит в `bitrix-loyalty-mvp/logs/portal-audit-2026-08-05/`, OAuth-часть - в `bitrix-loyalty-mvp/logs/portal-audit-2026-08-05/oauth/`.

Выводы по БП:

- Самые важные процессы действительно находятся не в кастомных VibeCode-роботах, а в стандартных шаблонах БП Bitrix24 по CRM-сущностям.
- Кастомных роботов/активностей приложения через `bizproc-robots` и `bizproc-activities` сейчас нет: API вернул пустые списки. Значит текущая автоматизация портала в основном сделана штатными роботами/БП Bitrix24 и внешними серверными webhook-интеграциями.
- `Перенос данных по лояльности в контакт [159]` имеет `autoExecute = 0`, поэтому сам по себе не запускается на каждое изменение сделки. По скриншоту он запускается из другого БП/робота. Это нормальная схема, но важно проверить точку вызова: на какой стадии и с какими условиями он стартует.
- Есть два активных шаблона `67` и `75`, которых нет в текущем списке шаблонов. Это похоже на старые/скрытые/удаленные шаблоны или шаблоны, которые не попали в обычную выдачу. Их нужно проверить в UI, потому что они массово висят на сделках и могут быть связаны с задержками, письмами, задачами или ожиданием оплаты/доставки.
- Процессы `139`, `141`, `153`, `165`, `157`, `187`, `145` автозапускаются. Это ядро автоматизации: оплата, доставка, склад, возвраты/обмены, процент лояльности, персонализация и партнеры.

## Лиды

Стадии лидов:

| Код | Стадия | Роль |
|---|---|---|
| `NEW` | Новое обращение | Входящий лид с сайта/формы/канала. |
| `IN_PROCESS` | В работе | Ручная обработка. |
| `CONVERTED` | Обработан | Успешная конвертация. |
| `JUNK` | Нецелевое обращение/спам | Закрытие без продажи. |
| `1` | Возврат | Негативная/служебная ветка возврата. |
| `2` | Обмен | Негативная/служебная ветка обмена. |

Подтвержденная логика:

- Интеграционный сервер принимает вебхуки Tilda:
  - `/api/tilda/order` - создание заказа/лида;
  - `/api/tilda/paid-order` - обновление после оплаты;
  - `/api/tilda/cart-start` - брошенная/начатая корзина;
  - `/api/tilda/register-contact` - регистрация контакта.
- При создании заказа сервер нормализует payload Tilda, ищет существующую цель по `tranid`, номеру заказа или Tilda order id, затем создает лид, если цель не найдена.
- В лид пишутся: номер заказа, Tilda order id, статус оплаты, сумма, товары, телефон/email, доставка, город, адрес, ПВЗ, промокод, скидки, бонусы, персонализация.
- По скриншоту в лидах есть робот на условии `Источник = Сайт v2sportdress.ru`, который меняет название на `Заказ {{Номер заказа}} | {{Город доставки}}`.
- В этой же цепочке лид дальше конвертируется/создает сделку в основной воронке заказов.

Узкое место:

- Переименование стоит на лиде и зависит от точного источника и готовности полей `Номер заказа` / `Город доставки` в момент срабатывания. Если сделка создается раньше, чем робот успел переименовать лид, или источник/поле не совпало, в сделку может уйти название только номером.
- В последних 500 сделках найдено 92 сделки в воронке `Заказы`, где название выглядит некорректно: только номер или `Сделка #...`. При этом номер заказа и город доставки в полях заполнены. Значит данные есть, но нет надежной страховки на уровне сделки.

Что поправить:

- Добавить резервный робот/БП в воронке `Заказы`: если `Название` не начинается с `Заказ`, а `Номер заказа` и `Город доставки` заполнены, установить `Название = Заказ {{Номер заказа}} | {{Город доставки}}`.
- Оставить робот в лидах, но не считать его единственной точкой нормализации.
- Для новых лидов проверить, что источник приходит именно кодом `1` / названием `Сайт v2sportdress.ru`, а не через другое поле или с задержкой.

## Воронка 1: Заказы

Стадии:

| Код | Стадия | Роль |
|---|---|---|
| `C1:NEW` | Подтверждение заказа | Заказ поступил, нужно проверить/подтвердить. |
| `C1:PREPARATION` | Сборка | Заказ собирается. |
| `C1:PREPAYMENT_INVOICE` | Лист ожидания | Ожидание товара/действия перед сборкой. |
| `C1:EXECUTING` | Готовы к отправке мастеру | Заказы с персонализацией передаются дальше. |
| `C1:FINAL_INVOICE` | Отправлены мастеру | Заказы у мастера. |
| `C1:UC_04FYEQ` | Ожидают отправки | Готовы к отгрузке клиенту. |
| `C1:UC_79WI97` | Отправлены | Переданы в доставку. |
| `C1:WON` | Доставлен/Вручен | Успешно закрытый заказ. |
| `C1:LOSE` | Отменен | Отмена. |
| `C1:UC_3RJ6OR` | Заказ не вручен | Неуспешная доставка. |
| `C1:UC_2HXNWZ` | Не оплачен | Неоплаченный заказ. |
| `C1:UC_ER41UI` | Старые заказы из удаленной воронки | Архивная/служебная стадия. |

Подтвержденная логика по интеграциям:

- Tilda создает лид, затем Bitrix-конвертация переносит его в сделку.
- После оплаты Tilda присылает отдельный вебхук `/api/tilda/paid-order`. Сервер ждет появление сделки и обновляет именно сделку, а не лид.
- По оплаченному вебхуку обновляются: сумма, `TRANID`, номер заказа, Tilda order id, трек, статус оплаты, доставка, город/адрес/ПВЗ/индекс, промокод, процент/сумма скидки, списанные бонусы, персонализация и товарные позиции.
- Если трека нет в payload, сервер пытается получить его в CDEK по `im_number = номер заказа`.
- Отдельный фоновый процесс восстанавливает статус оплаты: смотрит последние сделки в категории `1`, сверяет логи Tilda paid webhook и может перевести статус из `Ожидает оплаты` в корректное состояние.
- Есть интеграция CDEK: по трек-номеру обновляет поле `Статус доставки`, `Дата вручения заказа`, `Город/Пункт`, детали доставки и пишет лог в таймлайн.
- CDEK-статусы мапятся в поля Bitrix: `Создана накладная`, `Принят на складе отправителя`, `Готовится к отправке`, `В пути`, `Готов к выдаче`, `Вручен`, `Не вручен`.
- Для персонализации есть смарт-процесс мастера: по данным сделки создаются элементы `DYNAMIC_1038`, привязанные к сделке, с полями персонализации, вышивки, цвета, комментария, срока и размещения.

Лояльность в этой воронке:

- На сайте/в корзине отображаются доступные бонусы из контакта.
- Приветственные бонусы доступны только если начислены/доначисляемы и у контакта нет заказов.
- ДР-бонусы доступны, если начислены, не использованы, не сгорели и дата сгорания не прошла.
- Если у клиента есть и приветственные, и ДР-бонусы, они суммируются для применения в заказе: например 300, 500 или 800.
- При создании заказа через loyalty MVP создается сделка в Bitrix, сохраняются скидка по лояльности, промокод, сумма списанных бонусов, товары и затем финализируются бонусные поля контакта.
- Приветственные бонусы после первого заказа либо пишутся в `использовано`, либо в `сгорело`.
- ДР-бонусы при использовании пишутся в `Бонусы ДР использовано`; если срок прошел, остаток пишется в `Бонусы ДР сгорело`.
- По скриншоту БП `Перенос данных по лояльности в контакт` в сделках обновляет связанные поля контакта: количество заказов, сумма покупок, номер/дата/сумма последнего заказа, списано бонусов всего, затем запускает БП расчета процента лояльности.

Поля, которые меняются в заказе:

- `Номер заказа`, `Tilda Order ID`, `TRANID`.
- `Статус оплаты`.
- `Способ доставки`, `Стоимость доставки`, `Город доставки`, `Адрес доставки`, ПВЗ, индекс.
- `Трек-номер`, `Статус доставки`, `Дата вручения заказа`, `Город/Пункт`.
- `Промокод`, `Процент скидки по промокоду`, `Скидка по промокоду`.
- `Процент скидки по лояльности`, `Скидка по программе лояльности`.
- `Списано бонусов по заказу`, `Начислено бонусов по заказу`.
- Поля персонализации.

Узкие места:

- Название сделки иногда не нормализуется. По последним 500 сделкам: 92 некорректных названия, при этом номер/город есть.
- Пересчет контактной статистики сейчас разделен между Bitrix BP и серверной логикой. Это рабочая схема, но важно, чтобы у каждого поля был один “владелец”. Приветственные и ДР-поля должны вести сервер/loyalty MVP, а количество заказов, сумма покупок и процент скидки может вести BP.
- В БП по сделке нужно четко зафиксировать, какие стадии считаются покупкой. Если заказ попал в `Не оплачен`, `Отменен` или `Заказ не вручен`, он не должен увеличивать количество заказов/сумму покупок.
- Если заказ был сначала засчитан, а потом ушел в возврат/обмен/отмену, нужна отдельная обратная корректировка либо явное правило “история не пересчитывается”.
- CDEK-обновление статуса доставки обновляет поля, но по коду не видно автоматического перевода стадии сделки в `Доставлен/Вручен` или `Заказ не вручен`; вероятно, это делается роботами Bitrix. Нужно проверить в UI.

Что улучшить:

- Добавить страховочный deal-level робот названия.
- Сделать таблицу владения полями: Tilda-сервер, CDEK-синк, loyalty MVP, Bitrix BP.
- В БП “перенос лояльности в контакт” добавить/проверить условия по стадиям, чтобы статистика обновлялась только для финально оплаченных/валидных заказов.
- Для возвратов и отмен добавить корректирующий сценарий: минус сумма покупки, минус количество заказа или отдельное поле “сумма возвратов”, в зависимости от управленческой логики.
- Запустить регулярный аудит: некорректные названия, пустой город при номере заказа, отрицательные бонусы, расхождение `Начислено всего` и суммы бонусных полей, расхождение `Списано всего` и использовано/сгорело.

Подтвержденная логика:

- Для возвратов есть отдельные поля: `Основной заказ`, `Причина возврата`, `Сумма к возврату`, `Трек номер возврата`, `Статус доставки по возврату`, `Адрес пункта выдачи СДЭК`, `Требуется возврат денежных средств`.
- CDEK-синк определяет возвратный поток по категории `Возврат` и использует возвратный трек/возвратный статус вместо обычных полей доставки.
- При возвратном потоке CDEK может дописать адрес пункта выдачи СДЭК.

Узкие места:

- Не видно подтвержденного механизма обратного пересчета контактной статистики после завершенного возврата. Если основной заказ уже увеличил `Количество заказов` и `Сумму покупок`, то возврат может оставить клиента с завышенной историей покупок.
- Не видно подтвержденного правила по бонусам при возврате: возвращать использованные бонусы, не возвращать, списывать начисления, переносить в отдельное поле или учитывать только финансовый возврат.
- Если возврат превращается в обмен (`Нужен обмен`), есть риск двойного учета: возврат + новый обменный заказ.

Что улучшить:

- Ввести явную связь возврата с основным заказом как обязательную перед финансовой стадией.
- В момент `Возврат осуществлен` запускать корректирующий БП по основному контакту/заказу.
- Для бонусов выбрать одно правило и закрепить в автоматизации: например, если заказ полностью возвращен, использованные бонусы восстановить только если они еще в допустимом сроке/типе, а начисленные за заказ не применять.
- Добавить проверку, что один основной заказ не имеет несколько активных возвратов без причины.

## Воронка 5: Обмен

Стадии:

| Код | Стадия | Роль |
|---|---|---|
| `C5:NEW` | Заявка на обмен | Обмен создан. |
| `C5:UC_B5EWFG` | Товар возвращен(Сдэк) | Исходный товар пришел обратно. |
| `C5:UC_EEHTYL` | Товар принят на склад | Возврат принят складом. |
| `C5:UC_J22Q61` | Замена товара | Подбор/оформление замены. |
| `C5:UC_A9J6UG` | Отправлен мастеру на исправление | Сценарий исправления/персонализации. |
| `C5:PREPARATION` | Ожидает отправки | Новый товар готовится к отправке. |
| `C5:UC_EJGLG7` | Отправлен | Новый товар отправлен. |
| `C5:WON` | Доставлен/Вручен | Обмен завершен. |
| `C5:LOSE` | Обмен отменен | Обмен отменен. |

Подтвержденная логика:

- Для обмена используются поля основного заказа, причины обмена, товарных ID, возвратного трека и статуса возвратной доставки.
- CDEK-синк считает обмен возвратным потоком до исходящего этапа. Для исходящей стадии обмена можно использовать обычные поля доставки, если стадия входит в `exchangeOutboundStageIds`.
- В смарт-процессе мастера может создаваться отдельная карточка персонализации, если обмен требует исправления/персонализации.

Узкие места:

- Нужно проверить точный список `exchangeOutboundStageIds` в настройках сервера/портала. Если стадия исходящей отправки не указана, CDEK-синк может продолжать писать статус в возвратные поля.
- Не видно подтвержденного правила, влияет ли обмен на сумму покупок и количество заказов. Обычно обмен не должен создавать новую покупку, кроме доплаты.
- Если обмен оформляется через новую сделку заказа, может быть двойной учет в лояльности.

Что улучшить:

- Зафиксировать правило: обмен не увеличивает `Количество заказов` и `Сумму покупок`, кроме отдельного поля доплаты.
- В обменной воронке сделать обязательным поле `Основной заказ`.
- Проверить роботы стадий `Товар возвращен`, `Товар принят на склад`, `Отправлен`, `Доставлен/Вручен`: они должны менять именно логистические статусы обмена, а не обычную покупательскую статистику.

## Основная воронка 0: офлайн/персонализация

Стадии:

| `WON` | Вручен | Успешное закрытие. |
| `LOSE` | Отменен | Отмена. |

Подтвержденная логика:

- В loyalty MVP ручной заказ создается через `/api/orders`.
- Сделка создается в основной категории из настроек MVP, с названием вида `Офлайн заказ №... | филиал`, суммой к оплате, товарами, скидками, промокодом, списанными бонусами и полями доставки самовывоза.
- Перед созданием проверяется дубль по контакту/товарам/сумме.
- После создания финализируются приветственные и ДР-бонусы.

Узкие места:

- Основная воронка использует похожую логику лояльности, но другая точка создания заказа. Нужно держать единый набор правил для сайта и офлайн-заказов.
- Если контактная статистика обновляется BP только в воронке `Заказы`, офлайн-сделки могут не попадать в сумму покупок/количество заказов, если для категории 0 нет отдельного БП.

Что улучшить:

- Проверить, запускается ли БП переноса лояльности в контакт для категории 0.
- Если офлайн-заказы должны участвовать в лояльности, добавить отдельный BP или общий обработчик по успешной стадии `WON`.

## Смарт-процесс: Персонализация мастера

Стадии:

| Код | Стадия |
|---|---|
| `DT1038_15:NEW` | Новый заказ |
| `DT1038_15:PREPARATION` | В работе |
| `DT1038_15:SUCCESS` | Завершен |
| `DT1038_15:FAIL` | Провал |

Подтвержденная логика:

- Интеграционный сервер может создать элементы персонализации по сделке через `/api/master-personalization/create`.
- Элемент смарт-процесса привязывается к сделке, получает название, `xmlId`, стадию, карточку товара, персонализацию, вышивку, цвет, комментарий, срок и размещение.

Узкие места:

- Если поле персонализации в сделке пустое или не записалось из-за задержки Tilda/Bitrix, карточка мастера не создастся.
- Не видно обратной синхронизации статуса мастера в заказ: например, завершение персонализации автоматически переводит заказ из `Отправлены мастеру` в `Ожидают отправки`.

Что улучшить:

- Проверить робот на стадии завершения смарт-процесса мастера: должен возвращать заказ в правильную стадию.
- Добавить аудит заказов в стадии `Отправлены мастеру`, у которых все мастер-карточки уже завершены.

## Смарт-процесс: Выплаты партнерам

Стадии:

| `DT1042_17:SUCCESS` | Выплачено |
| `DT1042_17:FAIL` | Выплата отклонена |

Подтвержденная логика:

- В полях сделки заказа также есть промокод и скидка по промокоду, то есть связка с партнером возможна через код.

Узкие места:

Что улучшить:

- Создавать выплату только после финальной оплаченной стадии или ставить ее в `Новый заказ` до проверки срока возврата.
- При `Возврат осуществлен` проверять связанные выплаты и переводить в `Выплата отклонена` либо создавать отрицательную корректировку.

## Интеграции

### Tilda

Роль:

- Принимает создание заказа, старт корзины, оплату и регистрацию.
- Передает данные клиента, доставки, товаров, промокода, скидок, бонусов и персонализации.
- Для оплаченного заказа сервер обновляет уже созданную сделку, ожидая асинхронную конвертацию лида в сделку.

Риски:

- Разделение на `order` и `paid-order` правильно, но чувствительно к задержкам конвертации лида.
- Если Tilda не передает финальную сумму или доставку, нельзя пересчитывать ее на сервере “по-своему”: итог должна считать Tilda, сервер должен только принимать финальные поля и дополнительно учитывать бонусы.
- При сбоях в webhook важны replay-логи, иначе сделка останется без оплаты/треков/персонализации.

### CDEK

Роль:

- По треку или `im_number` получает заказ CDEK.
- Нормализует статус в Bitrix-поля.
- Для обычных заказов пишет дату вручения и город.
- Для возвратов/обменов использует возвратные поля.

Риски:

- Если трек пустой или CDEK не нашел заказ, статус не обновится.
- Если обменная исходящая стадия не настроена точно, статус может записаться в возвратные поля.
- Нужно проверить, какие роботы переводят стадию сделки на основании поля `Статус доставки`.

## Общие недочеты и рекомендации

1. Нужен доступ к точному списку роботов и BP.
   Текущий API-ключ не открыл `bizproc-templates` и `bizproc-robots`. Для полноценного аудита надо либо дать OAuth-ключ `vibe_app_*` с сессионным токеном, либо пройти по роботу в UI и выгрузить/зафиксировать настройки.

2. Добавить страховочные проверки на сделках.
   Главный пример - название заказа. Данные есть, но название иногда не собирается. Робот на сделке закроет это независимо от лида.

3. Развести владельцев полей.
   Сервер должен вести технические поля заказа/Tilda/CDEK и бонусные поля. Bitrix BP может вести агрегаты контакта: количество заказов, сумма покупок, процент скидки. Нельзя, чтобы одно поле считали два процесса.

4. Уточнить логику финальной покупки.
   Для лояльности надо строго определить, какие стадии считаются покупкой: вероятно, только оплаченный заказ, который дошел до `Доставлен/Вручен`, либо оплаченный заказ после отправки. Сейчас по скриншоту БП увеличивает счетчики при переносе данных из сделки, но нужно проверить условие запуска.

5. Описать правила возврата/обмена в автоматизации.
   Возврат и обмен должны корректировать статистику, выплаты и бонусы. Сейчас структура для этого есть, но точная обратная логика не подтверждена.

6. Сделать регулярный контроль качества данных.
   Минимальный ежедневный отчет:
   - сделки с названием только номером;
   - сделки с номером заказа без города доставки;
   - сделки `Оплачено`, но без контакта;
   - отрицательные бонусы;
   - `Начислено всего` не равно приветственные начислены + ДР начислены + начислено по заказам;
   - `Списано всего` не равно приветственные использовано/сгорело + ДР использовано/сгорело + списания по заказам, если такая формула утверждена;
   - возвраты без основного заказа;
   - обмены без основного заказа.

## Что проверить в Bitrix UI при следующем проходе

- Роботы в лидах на стадии `Новое обращение`: условие источника, порядок переименования и создания сделки.
- Роботы в воронке `Заказы`: создание задач, писем, переходы по CDEK-статусу, перенос лояльности в контакт.
- БП `Перенос данных по лояльности в контакт`: условия запуска, стадии, поля, защита от повторного запуска.
- БП `Расчет процента лояльности в контакте [157]`: формула процента, какие суммы учитываются.
- Роботы в `Возврат`: связь с основным заказом, финансовый возврат, корректировка контакта/партнера.
- Роботы в `Обмен`: связь с основным заказом, повторная отправка, влияние на статистику.
- Роботы смарт-процесса мастера: возвращает ли завершение персонализации заказ обратно в основную воронку.
- Роботы выплат партнерам: когда создается выплата и что происходит при возврате.
